The **studio** is the off-screen `TresCanvas` that renders a portrait. `PortraitStudio` is mounted once (the playground puts it in `app.vue`) and stays passive until `usePortraitStudio()` hands it a subject. The canvas itself exists only while bakes are pending.

```ts
import {
  PortraitStudio,
  PortraitSubject,
  PortraitBackground,
  PortraitLights,
  PORTRAIT_CAMERA,
  PORTRAIT_LIGHTS,
  PORTRAIT_RENDERING,
  frameFromHead,
} from '@artificer-forge/engine/runtime'
```

## `PortraitStudio`

The composition root. Mount it once. It owns the camera, the lights and the backdrop, and mounts a `PortraitSubject` whenever the shared studio state has an active descriptor:

```vue
<script setup lang="ts">
import { PortraitStudio } from '@artificer-forge/engine/runtime'
</script>

<template>
  <ClientOnly>
    <PortraitStudio />
  </ClientOnly>
</template>
```

### The canvas is on demand

The studio reads `active`, `pending`, `captured` and `failed` from `usePortraitStudio()`. The `TresCanvas` is rendered with `v-if="canvasAlive"`, and `canvasAlive` follows `pending`:

- `pending > 0`: the canvas mounts.
- `pending` drops to `0`: a timer starts, and the canvas unmounts after `IDLE_TEARDOWN_MS = 2_000`.

The canvas owns a whole WebGPU device. Mounted app-wide and always on, it would give every page a second device that re-uploads every texture the world scene already holds. `pending` (not `active`) is the signal because `active` drops to `null` between every capture: a party of four would tear the device down and rebuild it three times. The 2s hold covers two bursts that land a few hundred milliseconds apart (a portrait request right after the party's).

### Renderer

The canvas uses `createTransparentWebGPURenderer` (`alpha: true`, `antialias: true`). WebGPU is engine policy for every canvas: mixing WebGL and WebGPU canvases breaks skinned meshes because three's WebGPU backend converts glTF `skinIndex` buffers in place and the GLTF cache shares geometries across canvases. The transparent variant is used because the PNG is meant to composite over the page. There is no `preserveDrawingBuffer`: that is a WebGL context option, and a WebGPU canvas stays readable through `toDataURL` after present.

The wrapper div is `position: fixed; left: -9999px; width: 512px; height: 512px; opacity: 0; pointer-events: none`. Off-screen rather than `display: none`, so the render loop keeps drawing.

### `PORTRAIT_RENDERING`

Renderer state shared by the bake studio and the portrait lab (`apps/playground/pages/character/portraits.vue`). They must stay identical or the lab stops being WYSIWYG.

```ts
export const PORTRAIT_RENDERING = {
  toneMapping: ACESFilmicToneMapping,
  toneMappingExposure: 1.1,
  shadows: true,
  environmentIntensity: 0.1, // backdrop-driven scene.environment strength
}
```

::warning
Pass these **explicitly** to every portrait `<TresCanvas>` (`:tone-mapping`, `:tone-mapping-exposure`, `:shadows`). An omitted tone-mapping prop silently falls back to the TresJS default. ACES filmic was chosen because three's AgX is the flat base curve, not Blender's contrasty AgX, and ACES gets closest to the authored Blender reference portraits.
::

### Camera and error handling

- `framing` starts on a neutral placeholder and is overwritten by the subject's `@head` event the instant the model's head box resolves, so placeholder values never bake.
- The camera is driven **imperatively** (`cam.position.set`, `cam.fov`, `cam.lookAt`) in a `watchEffect`, because Tres does not re-apply `:look-at` when only the position changes. A yaw-orbited frame would otherwise capture facing front.
- Each bake mounts a fresh `PortraitSubject` (`:key="captureKey"`).
- The subject sits inside `<Suspense>`, and `onErrorCaptured` routes a load failure (bad model URL, Draco error) into `failed()`. Without that the bake promise would never settle and the serialized queue would deadlock.

## `PortraitSubject`

Loads the rig, plays idle, waits for the mesh assembly to settle, frames the head, and captures the frame. It is a child of the canvas (inside the `<Suspense>` boundary) because that is where the Tres context resolves.

| Prop | Type | Default | Purpose |
|------|------|---------|---------|
| `descriptor` | `PortraitSubjectDescriptor` | required | What to render (see below) |
| `autoCapture` | `boolean` | `true` | When `false`, render only (no `toDataURL` bake). The portrait lab uses this for live previews |

Emits:

| Event | Payload | Purpose |
|-------|---------|---------|
| `head` | `[Vec3, number]` | Head-mesh world-box centre + height. Drives the portrait camera |
| `bounds` | `[Vec3, Vec3]` | Full-model bounds. Used by the lab for the orbit target and readout only |
| `captured` | `[string]` | The PNG data URL once the frame is read |
| `failed` | `[unknown]` | A load or capture error |

The descriptor, as defined in `usePortraitStudio.ts`:

```ts
interface PortraitSubjectDescriptor {
  model?: string                  // single-GLB characters; omitted for modular ones
  appearance?: CharacterAppearance // modular characters: cosmetic recipe
  armor?: ArmorPiece[]            // modular characters: resolved armor pieces
  rig: string                     // 'Rig_Medium' | 'Rig_Large' | ...
  equipment: Equipment
  background?: string             // backdrop URL; undefined = transparent canvas
}
```

### Single-GLB or modular

The rig source is decided once at setup, mirroring `Actor.vue`:

- `appearance` present: `useModularRig(appearance, armor).rig` assembles the parts and armor on the shared skeleton.
- Otherwise: `useGLTF(model, { draco: true })` is awaited, and the rig is the named node `nodes[descriptor.rig]`.

`useEquipment(rig, equipment)` then attaches weapons, and `useCharacterAnimations(rig, rigSize)` loads the pack for the rig size (`descriptor.rig` with the `Rig_` prefix removed).

### Settling before capture

The subject gates on the `IDLE_A` action specifically, not on "any action loaded". Animation packs load **outside** `Suspense` and fill `actions` incrementally; signalling on the first available action risks capturing a bind pose.

Once idle plays, `whenSettled()` polls the rig every 150ms (first tick after 200ms) and counts meshes. Two consecutive identical counts (and at least one mesh) means the assembly has settled. Modular parts, armor and weapons attach asynchronously even after idle is ready, so framing straight away would measure an incomplete body. The poll gives up after 25 tries, well before the studio's 10s watchdog.

After settling the subject sets `castShadow` and `receiveShadow` on every mesh (self-shadowing of hair on forehead and chin on neck is a large part of the authored look), updates world matrices, emits `bounds` and `head`, then captures with two `requestAnimationFrame` calls: the first lets Tres draw with the new camera, the second guarantees the frame was presented before `toDataURL`.

## Head-mesh framing

Portraits are framed off the **head mesh's** world box, not the whole-model bounding box and not the head *bone*. The head mesh is consistent across bodies, equipment and poses, and it scales to the actual head size. Keying off the head bone overshoots tall rigs: a werewolf's head bone sits high on long legs, but its head is not proportionally bigger.

`findHeadMesh` picks the first mesh whose name matches `/head/i`, preferring a `SkinnedMesh` so a helmet or accessory named "...head..." cannot win. With no head mesh (custom rig) the subject falls back to the upper 30% of the bounding box.

`frameFromHead(center, headHeight, opts?)` turns a head box into a `PortraitFraming` (`cameraPosition`, `lookAt`, `fov`). Offsets are fractions of head height, so the same knobs hold across rig sizes (Medium head about 1.0, Large about 1.5). The defaults live in `PORTRAIT_CAMERA`:

```ts
export const PORTRAIT_CAMERA = {
  headLift: 0,              // shift the look point above/below the head centre
  viewHeight: 1.4,          // vertical slice to fit, as a multiple of head height
  fov: 10,                  // field of view (deg); long lens = flat portrait perspective
  cameraHeightOffset: 0.05, // camera height vs look point
  yaw: 20,                  // horizontal orbit angle for a 3/4 view
}
```

Pass a `FrameOptions` partial (`Partial<typeof PORTRAIT_CAMERA>`) as the third argument to override any of these. The model is assumed to face +Z (Three/GLB convention), so the camera is placed in front of the face.

::tip
Framing changes apply on the next bake. Bump `PORTRAIT_CACHE_VERSION` in `portraitSignature.ts` so cached portraits re-bake, or clear `localStorage['af:portraits']`.
::

## `PortraitLights`

Shared lighting used by both the bake studio and the portrait lab. The drama comes from a high key-to-fill ratio plus warm/cool contrast: a strong warm shadow-casting key models the face, a dim cool fill barely lifts the shadow side, a cool rim carves a bright edge, and a faint warm hemisphere stands in for ground bounce so shadows never crush to black.

| Light | Role | Intensity | Colour | Position |
|-------|------|-----------|--------|----------|
| `TresHemisphereLight` | warm bounce | `0.35` | sky `#eed9bd`, ground `#5a4030` | n/a |
| `TresDirectionalLight` (key) | warm key, casts shadows (2048 map) | `2.5` | `#ffd9a3` | `[3.5, 4, 2.5]` |
| `TresDirectionalLight` (fill) | cool fill, opposite the key | `0.2` | `#9fb8ff` | `[-3.5, 0.5, 2]` |
| `TresDirectionalLight` (rim) | cool backlight | `1.8` | `#cfe0ff` | `[-1.5, 3, -4]` |

The values come from `PORTRAIT_LIGHTS`. Every intensity and colour is also a prop (`keyIntensity`, `keyColor`, `fillIntensity`, `fillColor`, `rimIntensity`, `rimColor`, `bounceIntensity`) so the lab can tune them live.

::note
Warmth gotcha: under ACES an overexposed warm light bleaches to **white**. For a warmer face, deepen `keyColor` toward orange or lower key intensity/exposure. Cranking the key makes it colder.
::

## `PortraitBackground`

A flat backdrop rendered as a **child of the portrait camera**, so it is camera-local: a plane at `-Z` always faces the lens and fills the frame regardless of how the camera was orbited.

| Prop | Type | Default | Purpose |
|------|------|---------|---------|
| `framing` | `PortraitFraming` | required | Current camera framing, used to size and place the plane in the frustum |
| `src` | `string` | required | Backdrop texture URL |
| `envIntensity` | `number` | `PORTRAIT_RENDERING.environmentIntensity` (`0.1`) | `scene.environmentIntensity`; the lab overrides it for live tuning |

The plane uses an unlit `TresMeshBasicMaterial` with `:tone-mapped="false"`, so the portrait lights never tint the backdrop, and the texture is decoded in `SRGBColorSpace`. It is pushed to `1.8 x` the camera-to-subject distance (so the body never clips through) and sized to the vertical FOV at that depth plus 15% padding.

### The backdrop doubles as `scene.environment`

A clone of the backdrop texture is set to `EquirectangularReflectionMapping` and assigned to `scene.environment`, at `scene.environmentIntensity = envIntensity`. The subject picks up the backdrop colours as ambient bounce: a red backdrop gives a red-tinted shadow side, which is the Blender-GI look of the authored portraits. A flat image as an equirect is geometrically wrong, but at `0.1` it only reads as a soft colour cast. Both textures are disposed and `scene.environment` reset on unmount.

### Resolving the backdrop

Each character can author a backdrop on its entity YAML via `portraitBackground`. `resolvePortraitBackground()` resolves it, falling back to a shared default so every portrait gets a backdrop:

```ts
import { resolvePortraitBackground, DEFAULT_PORTRAIT_BACKGROUND } from '@artificer-forge/engine/runtime'

resolvePortraitBackground('/img/portraits/bgs/dark-forest.png') // -> the authored URL
resolvePortraitBackground(undefined) // -> '/img/portraits/bgs/default.png'
```

::warning
The backdrop is part of the **appearance**, so it is folded into the [signature](/portraits/signature). Changing or adding a backdrop re-bakes the portrait.
::
