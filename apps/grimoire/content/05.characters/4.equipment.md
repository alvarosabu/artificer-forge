---
title: Equipment
description: How equipped item entities become meshes, weapons on hand bones through useEquipment and body armor on modular characters through useModularArmor.
---

Equipment is the visual layer over the [item-entity model](/inventory/overview). An item entity with `containerId = characterId` and a `slot` is "equipped". Two composables turn those items into meshes:

| Slots | Composable | Mechanism |
|-------|------------|-----------|
| `mainHand`, `offHand` | `useEquipment` | Loads the weapon's `model` GLB and parents it to a hand bone. Works on both rig paths |
| `helmet`, `armor`, `cloak`, `trousers`, `gauntlets`, `boots` | `useModularArmor` + `useModularRig` | Skinned meshes from `item.modular.assets`, rebound to the shared skeleton, hiding covered body segments. Modular characters only |
| `amulet`, `ring1`, `ring2` | none | Stat-only (armor pools). Nothing rendered |

On a single-GLB character (`hero.glb`), body slots still exist in the store and the doll, but no mesh changes.

## Slots and validation

The store knows eleven slots:

```ts
export type EquipmentSlotKey =
  | 'mainHand' | 'offHand' | 'helmet' | 'armor' | 'cloak' | 'trousers'
  | 'gauntlets' | 'boots' | 'amulet' | 'ring1' | 'ring2'
```

A character template lists the slots it owns in `equipmentSlots`; `moveItem` returns `{ ok: false, reason: 'no-slot' }` for the others. `isItemTypeForSlot` matches by `subtype`: `weapon` → mainHand/offHand, `ring` → ring1/ring2, otherwise `subtype === slot` (`helmet`, `armor`, `cloak`, `trousers`, `gauntlets`, `boots`, `amulet`).

```ts
gameStore.equipItem(itemEntityId, 'armor')   // item must already belong to the character
gameStore.unequipItem(itemEntityId)          // back into the same bag
```

Both wrap `moveItem`, which also swaps out an occupant and refills the armor pools (`refreshArmor`). See [Store API](/inventory/store-api).

## Weapons: `useEquipment`

```ts
export function useEquipment(
  rig: Ref<TresObject3D | undefined>,
  equipment: Ref<Equipment | undefined>,
  activeSlot?: Ref<'mainHand' | 'offHand' | 'none' | undefined>,
  options: UseEquipmentOptions = {},
)

export interface Equipment { mainHand?: string, offHand?: string }   // item templateIds
export interface UseEquipmentOptions {
  onAttach?: (object: Object3D) => void   // runs on every freshly attached weapon scene
}
```

| Param | Type | Default | Purpose |
|-------|------|---------|---------|
| `rig` | `Ref<TresObject3D>` | required | Armature root; `useGraph(rig)` finds the bones |
| `equipment` | `Ref<Equipment>` | required | `{ mainHand, offHand }` templateIds, from `gameStore.derivedEquipment(id)` |
| `activeSlot` | `Ref<'mainHand' \| 'offHand' \| 'none' \| undefined>` | `undefined` | Which weapon is visible. `undefined`/`null` = both, `'none'` = neither, a slot = only that one |
| `options.onAttach` | `(Object3D) => void` | none | Hook for material swaps on the attached scene |

`Equipment` is a projection, not stored state. The truth is the item entities; `derivedEquipment` reads `equippedAt(id, 'mainHand')` and `equippedAt(id, 'offHand')`.

### How `Character.vue` calls it

```ts
const equipment = computed(() => gameStore.derivedEquipment(entity.value?.id ?? ''))
const { activeWeaponSlot } = useActionBar()
const isLeader = computed(() => gameStore.party.leader === props.entityId)
const effectiveWeaponSlot = computed(() => isLeader.value ? activeWeaponSlot.value : undefined)

useEquipment(rig, equipment, effectiveWeaponSlot, {
  onAttach: (object) => {
    if (props.grading) applyGradingToModel(object, props.grading, { groundHeight: props.groundHeight ?? undefined })
  },
})
```

Only the party leader follows the action bar's weapon tab; other party members show both hands. `onAttach` is where the stylized grading reaches weapon materials; without it, a graded scene would render weapons with their raw PBR look. `Actor` calls `useEquipment(rig, equipment)` with no active slot.

### Attach sequence

1. `useGraph(rig)` builds a name → node dictionary. Bones: `handslotr` (main hand), `handslotl` (off hand). Blender drops the dot from `handslot.r` on export.
2. On `graph.nodes` becoming available, attach whatever `equipment` holds. Later `equipment` changes (deep watch) call `syncSlot` per slot: new id → attach, missing → detach.
3. `attach` resolves the item template through `gameStore.resolveTemplate(templateId)` and loads `template.model` with a `GLTFLoader` + `DRACOLoader` (Google CDN decoder). A per-slot request counter drops stale loads if the slot changed in between.
4. The loaded scene is cloned, every mesh gets `castShadow = true`, `onAttach` runs, `bone.add(scene)`, then `applyVisibility()` applies `activeSlot`.
5. `detach` removes the object and disposes geometry, materials and every `Texture` on them. `onScopeDispose` detaches both slots.

Why `GLTFLoader` and not `useGLTF`: `useGLTF` resolves its path once and never reloads. Weapons swap at runtime, so the composable needs to load on demand.

### Weapon templates

Weapons need `model`:

```yaml
# content/entities/items/weapons/shortsword.yaml
templateId: shortsword
type: item
subtype: weapon
name: Shortsword
icon: /img/items/shortsword.png
model: /models/items/weapons/Sword_1Handed.glb
damage:
  dice: "1d8"
  type: slashing
```

`Character` also exposes `attachToHand(slot, object)` / `detachFromHand(slot)` for ad-hoc props on the same bones, tracked separately from equipment.

## Body armor: `useModularArmor`

```ts
export function useModularArmor(entityId: MaybeRefOrGetter<string>): ComputedRef<ArmorPiece[]>

export interface ArmorPiece {
  id: string          // filename stem of the GLB
  path: string        // from item.modular.assets
  hides: string[]     // body segments to hide
  tint?: string | null // palette-atlas URL, null = the piece's embedded atlas
}
```

For each of `helmet, armor, cloak, trousers, gauntlets, boots` it reads `gameStore.equippedAt(id, slot)` and, if the item has a `modular` block:

1. Picks the fitted mesh: `mod.assets[entity.sex] ?? mod.assets.any`. No match → `console.warn` once per `templateId:sex` and the piece is skipped (the item still counts for armor pools).
2. Reads `entity.appearance.equipmentTint[slot]`, looks it up in `item.texture.tints`, and passes the atlas URL as `tint`.
3. Emits `{ id, path, hides, tint }`.

The computed is reactive, so equipping in the inventory modal re-dresses the character in the scene at once. `useModularRig(appearance, armorPieces)` consumes the list: it loads and rebinds the pieces, hides the body segments listed in `hides` (only for pieces that finished loading, or limbs would flash invisible), tints exposed `Skin` materials (sandals with toes), and swaps `map` on the piece's materials to the tint atlas. Mechanics: [Modular characters](/characters/modular-characters).

### Item contract

```yaml
# content/entities/items/armor/leather-jerkin.yaml (excerpt)
subtype: armor           # must equal the slot name
modular:
  slot: armor
  hides: [torso]         # side-agnostic keys hide both sides; armL / footR hide one
  assets:
    M: /models/characters/armors/ARM_M_Leather_Jerkin.glb
    F: /models/characters/armors/ARM_F_Leather_Jerkin.glb
texture:
  base: /models/characters/textures/leather_jerkin_texture.png
  tints:
    - { id: black, label: Black, map: /models/characters/textures/leather_jerkin_black.png }
    - { id: crimson, label: Crimson, map: /models/characters/textures/leather_jerkin_crimson.png }
```

| Field | Purpose |
|-------|---------|
| `modular.slot` | One of the six body slots |
| `modular.hides` | Segment keys from `head, torso, hips, arm(L/R), hand(L/R), leg(L/R), foot(L/R)` |
| `modular.assets` | `M`, `F`, `any`. Unisex pieces (Cedric's set) use `any` only; sexed pieces need both `M` and `F` or one sex renders nothing |
| `modular.rig` | `medium` (default) or `small`. The customizer refuses cross-rig pieces (`fitsRig`); the engine does not check, a small-rig mesh on a medium skeleton deforms |
| `texture.base` | The atlas embedded in the GLB, listed so tools can preview it |
| `texture.tints[]` | Alternate recoloured atlases selectable by id in `appearance.equipmentTint` |

Coverage examples from the playground: `cedric-cloak` hides `[]`, `wild-raider-gauntlets` (bracers) hides `[]`, `cedric-gauntlet` hides `[armL]`, `common-pants` hides `[hips, leg]`, `leather-sandals` hides `[foot]` and brings its own toes.

## Starting equipment

```yaml
# content/entities/characters/companions/tav.yaml (excerpt)
equipmentSlots:
  - mainHand
  - offHand
  - helmet
  - armor
  - trousers
  - gauntlets
  - boots
  - amulet
  - ring1
  - ring2

equipment:
  mainHand: shortsword
  armor: leather-jerkin
  trousers: common-pants
  boots: leather-sandals
```

`spawnFromTemplate` walks `ALL_EQUIPMENT_SLOTS`, calls `spawnItemEntity(itemTemplateId, { containerId, slot })` for each filled entry, then `refreshArmor(id)`. Tav has no `cloak` slot, so a cloak dragged onto him fails with `no-slot`; Cedric lists all eleven.

## The inventory doll

`CharacterPreview` (`@artificer-forge/engine/ui`) renders the character in the inventory modal on its own `TresCanvas`. It picks the model component by the same rule as the scene:

- `entity.appearance` present → `ModularCharacterPreviewModel`: its own `useModularRig(appearance, useModularArmor(id))` clone (a Three object cannot live in two scenes), plus `useEquipment(rig, equipment)` and `useCharacterAnimations(rig, 'Medium')` for the idle.
- otherwise → `CharacterPreviewModel` with `model-url`, `rig-key` and `equipment` props.

`ModularCharacterPreviewModel` is internal to `CharacterPreview` and not exported from `ui/index.ts`. See [Inventory UI Components](/inventory/ui-components).
