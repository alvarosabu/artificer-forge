The runtime side is two halves: `useSurface` (the singleton engine that owns the grid, textures and sim loop) and `SurfaceSystem.vue` (a pure renderer that consumes the engine's textures). Both come from `@artificer-forge/engine/runtime`.

## SurfaceSystem is a default system

`SurfaceSystem` is one of the two default systems `<Game>` mounts when you do not provide a `#systems` slot (`packages/engine/src/Game.vue`):

```vue
<slot v-if="$slots.systems" name="systems" />
<template v-else>
  <CombatSystem />
  <SurfaceSystem />
</template>
```

The switch is keyed on slot **presence**, not slot output. A plain `<slot name="systems">` with fallback content would fall back whenever your slot renders nothing (for example a `v-if` that is false), and `CombatSystem`'s ground-click plane would silently outrank a scene's own terrain. With the presence check, an empty `#systems` really means "no default systems".

So **any scene under `<Game>` renders surfaces with no extra wiring**. You add `SurfaceSystem` yourself only when you provide `#systems` and compose a custom set. Drop it inside the Tres scene graph (it needs `useLoop`, which must run in a Tres component context):

```vue
<template>
  <SurfaceSystem :billboard-density="5" />
</template>
```

`billboardDensity` (default 5) is flame billboards per m² of field, a coverage/perf knob, not a per-pool count.

The component reads the engine's `texture`, `fireTexture`, `stateTexture`, `dimensions` and `isActive`, builds the pool/charcoal/fire/ember/billboard meshes only while a surface `isActive`, and drives the sim via `useLoop`:

```ts
const { texture, fireTexture, stateTexture, dimensions, isActive, tick } = useSurface()
const { onBeforeRender } = useLoop()
onBeforeRender(({ delta }) => tick(delta))
```

Idle scenes hold the mesh set at `null` → zero draw calls. `SurfaceSystem` is a pure renderer with no pointer handlers, so clicks fall through to a scene's own paint/move plane.

### What it builds

When `isActive` flips true, a `watchEffect` builds one mesh set for the whole field (`width × depth` from `dimensions`). Every rebuild disposes the previous set, and `onUnmounted` disposes the last one, so activation cycles and route changes do not leak GPU buffers.

| Mesh | Geometry | Material / factory | Y | `renderOrder` |
|------|----------|--------------------|---|---------------|
| `poolMesh` | `PlaneGeometry(width, depth)` | `buildPoolSurfaceMaterial(texture, stateTexture, lightningTex)` | 0.01 | 0 |
| `charcoalMesh` | `PlaneGeometry(width, depth, 160, 160)` | `buildCharcoalSurfaceMaterial(fireTexture)` | 0.012 | 1 |
| `fireMesh` | `PlaneGeometry(width, depth)` | `buildFireSurfaceMaterial(fireTexture)` | 0.02 | 2 |
| `emberMesh` | `InstancedMesh` | `createInstancedEmberSystem(width, depth, fireTexture)` | shader | 3 |
| `flameBillboards` | `InstancedMesh` | `createFireBillboards(width, depth, fireTexture, count, spawnRadius, flipbook)` | shader | 4 |

All planes are rotated `-Math.PI / 2` and sit at the XZ origin. The charcoal material samples `positionWorld.xz` and `positionLocal.xz` with the same noise, so the mesh must stay at x=0, z=0.

**Render order is pinned on purpose.** Every layer is transparent, and Three's distance sort cannot order them: the ember and billboard instances are positioned in the shader, so their bounding spheres sit at the mesh origin and tie with the plane centres. Explicit `renderOrder` values replace the sort. Charcoal still draws before the flames (its `depthWrite` occludes flames behind the coal humps); flames and embers draw last so a sort tie can never bury them under the bed. If you add your own transparent layer to the field, pick a `renderOrder` relative to this table.

**Flame count and spread are derived from the field**, not per pool:

```ts
createFireBillboards(
  width,
  depth,
  fireTex,
  Math.round(width * depth * billboardDensity), // count
  Math.max(width, depth) / 2,                   // spawnRadius
  flipbook,
)
```

One field-wide cluster covers the whole grid; each billboard reads `firePresence` in the shader and hides itself where the fire texture is empty. That is why flames appear over any fire cell, declared or painted, without the renderer knowing where the pools are. A hidden billboard still rasterizes, so `billboardDensity` trades fill-rate for denser flames.

### Lazy textures

Two textures load only after the first time `isActive` becomes true, and only once each. Non-surface scenes never fetch them, and `Game.vue` needs no `<Suspense>` boundary because there is no top-level `await`.

| Texture | File | Settings | Consumer |
|---------|------|----------|----------|
| Flame flipbook | `/textures/flipbook/flame03/Flame03_16x4.tga` (via `TGALoader`) | `SRGBColorSpace` | `createFireBillboards` |
| Lightning sprite | `/textures/electricity/spark_05.png` | `NoColorSpace`, `RepeatWrapping` on both axes | `buildPoolSurfaceMaterial` (electrified pools) |

The load is gated on `isActive`, not on a declared fire source, because fire can be painted at any time. Until the flipbook arrives the pool, charcoal, fire and ember meshes already render; `flameBillboards` stays `null` and fills in on the next rebuild. The lightning sprite is an intensity mask (not colour), so it stays in `NoColorSpace`; repeat wrapping lets the pool material layer it at several scales and rotations into arcs.

## useSurface: the engine

`useSurface()` returns the app-lifetime singleton engine. First call (from `SurfaceSystem`'s setup) builds it inside a detached `effectScope` so its hydration watchers survive route changes.

| Member | Purpose |
|--------|---------|
| `field` | `ShallowRef<SurfaceField>`: the raw `grid` plus the three textures and their backing `Float32Array`s. Replaced wholesale when `gridConfig` changes, so hold the ref, not `field.value` |
| `texture` / `fireTexture` / `stateTexture` | `DataTexture`s the renderer samples (pool channels, fire, variant state). Computed from `field` |
| `dimensions` | World-space field extent `{ width, depth }` = `cols * cell`, `rows * cell` from `useSurfaceStore().gridConfig` |
| `isActive` | Readonly: true whenever the grid holds any surface (hydrated or painted) |
| `sample(x, z)` | Read the cell under a world point |
| `seed(x, z, kind)` | Live paint: spreads + decays per kind |
| `event(x, z, event)` | Apply a `'lightning'` / `'cold'` event at a point (flood-fills the liquid pool) |
| `clear()` | Wipe all live grid state |
| `tick(delta)` | Advance the sim, re-pack textures, apply standing statuses |

`tick` runs the sim (`step`), repacks the three textures, and applies surface statuses to character entities each frame (`statusForCell` + the `warm` radiant-heat check). The idle guard on `isActive` means non-surface scenes pay almost nothing.

## Two ways to populate the field

**Declarative (level data)**: push `SurfaceSourceDef[]` into `useSurfaceStore`; `useSurface` watches the store and hydrates the grid. `lifetime` omitted ⇒ permanent pool. `frozen`/`electrified` pre-place the variant state.

```ts
import { useSurfaceStore } from '@artificer-forge/engine/runtime'
import type { SurfaceSourceDef } from '@artificer-forge/engine/core'

const surfaceStore = useSurfaceStore()
const surfaces: SurfaceSourceDef[] = [
  { kind: 'water', x: -4, z: -4, radius: 4 },                 // permanent pool
  { kind: 'water', x: 0, z: -5.5, radius: 3, frozen: true },  // ice sheet
  { kind: 'blood', x: 0, z: 5.5, radius: 3, electrified: true }, // charged hazard
]
surfaceStore.setSources(surfaces) // call surfaceStore.clearSurfaces() on unmount
```

**Live paint**: call `seed` / `event` directly from a pointer handler; this is runtime state (not store data), so it spreads and decays per kind:

```ts
const { seed, event } = useSurface()

function onPaint(e) {
  if (!e.point) return
  if (tool === 'paint') seed(e.point.x, e.point.z, kind)
  else event(e.point.x, e.point.z, tool) // 'lightning' | 'cold'
}
```

::warning
The engine is a **singleton**: live-painted state persists across scenes. Call `clear()` (paint scenes) or `surfaceStore.clearSurfaces()` (declarative scenes) on unmount so it doesn't leak into the next page.
::

::note
The textures are rendered by `@artificer-forge/vfx` materials (`buildPoolSurfaceMaterial`, `buildFireSurfaceMaterial`, etc.). See [Textures](/surfaces/textures) for the cell → channel mapping.
::
