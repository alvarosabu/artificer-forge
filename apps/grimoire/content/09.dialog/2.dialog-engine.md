The dialog runtime splits into two layers, both exported from `@artificer-forge/engine/runtime`:

- **`useDialogStore`**: the stateful Pinia store. Holds the active tree, the current node, and the player-facing getters. This is what your page and the HUD talk to.
- **`useDialogEngine`**: pure, stateless logic the store leans on: building the dialog context, resolving text, gating choices, rolling skill checks, applying effects. You rarely call it directly; the store wires it up for you.

```ts
import { useDialogEngine, useDialogStore } from '@artificer-forge/engine/runtime'
```

## The store

### State

| Member | Type | Meaning |
|--------|------|---------|
| `activeTree` | `DialogTree \| null` | The currently playing tree (`dialogId`, `startNode`, `nodes`) |
| `currentNodeId` | `string \| null` | Id of the node being shown |
| `speakerEntityId` | `string \| null` | The resolved speaker entity for this dialog |
| `history` | `DialogHistoryEntry[]` | Lines + chosen replies, in order |
| `lastCheck` | `CheckRoll \| null` | Most recent skill-check result (auto-clears after 2.5 s for the panel flash) |

### Getters

| Getter | Type | Meaning |
|--------|------|---------|
| `isOpen` | `boolean` | True while a tree + node are active |
| `currentNode` | `DialogNode \| null` | The active node object |
| `currentText` | `string` | Resolved text for the current node (honors `textVariants`) |
| `currentChoices` | `ResolvedChoice[]` | Visible, condition-evaluated choices (hidden ones filtered out) |
| `currentSpeakerEntity` | `EntityState \| null` | The speaker entity, resolved by id then `templateId` |

### Actions

| Action | Signature | Effect |
|--------|-----------|--------|
| `open` | `(dialogId: string, speakerId: string \| null) => Promise<void>` | Resolves the tree via the game store, blocks input, enters the start node |
| `choose` | `(choiceIndex: number) => void` | Picks a choice: applies its effects, rolls any check, branches to the next node |
| `close` | `() => void` | Tears down the dialog and unblocks input |

::note
`open` is re-entry safe: if a dialog is already open it returns early, so a repeated interaction can't clobber live state. The tree is fetched through `gameStore.resolveDialog(dialogId)`; a missing tree logs a warning and bails. See [How a tree reaches the runtime](/dialog/overview#how-a-tree-reaches-the-runtime) for the resolver wiring.
::

## Starting and advancing a dialog

```ts
const dialogStore = useDialogStore()

// Start: pass the dialog id and the speaking entity (e.g. an NPC instance id).
await dialogStore.open('elder_greeting', npcEntityId)

// The HUD reads these reactively:
dialogStore.currentText      // line for the current node
dialogStore.currentChoices   // ResolvedChoice[] the player can pick

// Advance by choosing — index is the choice's `index` field, not the array position.
dialogStore.choose(choice.index)

// Bail out at any point.
dialogStore.close()
```

### Entering a node

`enterNode(nodeId)` is internal, but its rules decide when a dialog ends:

- `__end` is a sentinel id. Entering it calls `close()`.
- An id that is not in `activeTree.nodes` logs `[dialog] node not found` and calls `close()`.
- Otherwise the node's resolved text is pushed to `history` and its on-entry `effects` run. An `endDialog` effect there closes at once.

### Choosing

`choose` walks one step:

1. Ignores the call if the index is out of range or the choice is not `available`.
2. Records the player's reply on the latest `history` entry.
3. Applies the choice's `effects` (costs/triggers fire for every choice, before branching). `endDialog` here closes before any roll.
4. If the choice has a `check`, rolls it (`rollCheck`), flashes the result, then follows `onSuccess` / `onFailure`: applies that branch's `effects`, then enters its `next`. **A branch without `next` closes the dialog.** So a failure branch with only effects and no `next` ends the conversation.
5. Otherwise follows `choice.next`. A missing `next` (or `__end`) ends the dialog.

## Node and choice shape

The engine's types (from `useDialogEngine`) describe an authored node:

```ts
interface DialogNode {
  speaker?: string                     // templateId of the speaker; omit = narrator
  text: string
  textVariants?: { if: Record<string, unknown>, text: string }[]
  cameraShot?: 'three-quarter' | 'over-shoulder' | 'closeup' | 'wide' | 'two-shot'
  cameraTarget?: string                // accepted, but not read by the camera (see below)
  choices?: DialogChoice[]
  effects?: Record<string, unknown>[]  // on-entry effects
}

interface DialogChoice {
  text: string
  tagPrefix?: string                   // e.g. [PERSUASION] label
  conditions?: Record<string, unknown>[]
  check?: { skill: string, dc: number, advantage?: boolean }
  next?: string
  onSuccess?: { next?: string, effects?: Record<string, unknown>[] }
  onFailure?: { next?: string, effects?: Record<string, unknown>[] }
  effects?: Record<string, unknown>[]
  lockedDisplay?: 'hide' | 'lock'      // hide a failed-condition choice, or show it locked (default)
}
```

::warning
`cameraTarget` is dead data today. The type, the Nuxt Content schema and the editor inspector all accept it, but `useDialogCamera` never reads it: the framing target is always the entity matched from `node.speaker`. Set `speaker` if you want the camera to move.
::

`textVariants` are tried in order; the first entry whose `if` condition passes wins, else `node.text` is used. Each `if` is one condition object with the same keys as `choice.conditions[i]`.

## How the engine resolves a choice

`useDialogEngine` is where the logic lives. The store calls these for you, but they describe exactly what happens:

| Function | Purpose |
|----------|---------|
| `buildContext(speakerId)` | Builds `DialogContext`: `player` (party leader), `speaker`, `partyEntities`, `gameStore` |
| `resolveText(node, ctx)` | Returns the first matching `textVariants` entry, else `node.text` |
| `availableChoices(node, ctx)` | Evaluates each choice's `conditions` into a `ResolvedChoice` (`available`, `lockedReason`, `hide`) |
| `rollCheck(check, ctx)` | d20 (+ advantage) plus the skill's stat modifier vs `dc` → `CheckRoll` |
| `applyEffects(effects, ctx)` | Mutates game state; returns `{ endDialog }` |
| `evaluateConditions(conditions, ctx)` | True if every condition passes |

`player` is always the **party leader**. Every `class`, `race`, `stat`, `hasItem` and similar check reads the leader, not the selected entity.

### Conditions

`conditions` is an array; **all** entries must pass (AND). One entry is an object with one or more keys; all keys inside must pass too. The first failing entry produces the `lockedReason` shown by the panel.

| Key | Shape | Passes when | `lockedReason` |
|-----|-------|-------------|----------------|
| `flag` | `'name'` | `gameStore.hasFlag(name)` is true | `Story requirement` |
| `flag` | `{ name: value }` | `gameStore.getFlag(name) === value` for every entry (strict equality) | `Story requirement` |
| `notFlag` | `'name'` | `hasFlag(name)` is false | `Story requirement` |
| `class` | `'fighter'` | `player.class === value` | `Requires fighter` |
| `race` | `'elf'` | `player.race === value` | `Requires elf` |
| `faction` | `'watch'` | `player.faction === value` | `Requires watch faction` |
| `hasAbility` | `'dash'` | `player.abilities` includes it | `Requires ability: dash` |
| `hasStatusEffect` | `'wet'` | `player.statusEffects` has an entry with that `id` | `Requires status: wet` |
| `stat` | `{ strength: { gte: 14 } }` | every comparison holds; ops `gte`, `lte`, `gt`, `lt`, `eq`; missing stat reads as `0` | `strength ≥ 14` |
| `partyHas` | `'cleric'` | some party entity has that `class` **or** `templateId` | `Need cleric in party` |
| `hasItem` | `{ id: 'gold', qty: 10 }` | leader's items (equipped included) with that `templateId` sum to at least `qty` (default 1) | `Need 10× gold` |

Two `flag` forms exist. The string form is a truthy test. The object form compares with `!==`, so `{ flag: { gold_paid: 10 } }` fails if the flag holds `"10"` or `true`. Use `clearFlag` (not `setFlag: false`) when a later `notFlag` must pass, because `notFlag` only checks `hasFlag`.

::caution
An unknown condition key logs `[dialog] unknown condition key` and **fails the whole condition**. The choice locks (or hides) and its `lockedReason` is the raw key name. A typo like `hasItems` silently locks the option.
::

### Skill checks

`rollCheck` maps a skill to a stat, reads the leader's stat, derives the modifier `floor((stat - 10) / 2)`, rolls a d20 (twice and takes the max when `advantage`), and compares `roll + modifier` to `dc`. Success is `total >= dc`. The result lands in `lastCheck`, and the success/failure branch decides the next node.

| Stat | Skills |
|------|--------|
| `strength` | `athletics` |
| `dexterity` | `acrobatics`, `sleight-of-hand`, `stealth` |
| `intelligence` | `arcana`, `history`, `investigation`, `nature`, `religion` |
| `wisdom` | `animal-handling`, `insight`, `medicine`, `perception`, `survival` |
| `charisma` | `deception`, `intimidation`, `performance`, `persuasion` |

Fallback rules:

- A skill that is not in the table is used **as the stat name** (`{ skill: 'strength', dc: 12 }` reads `stats.strength`).
- A stat the leader does not have reads as **10**, so the modifier is 0.
- `constitution` has no skill mapped to it; use it directly as the skill name.

### Effects

`applyEffects` runs an array of effect objects against the context. Effects fire on node entry, on choosing, and inside `onSuccess` / `onFailure`. Each object can hold several keys; they run in object order.

| Key | Payload | What it does |
|-----|---------|--------------|
| `setFlag` | `{ name: true \| false \| number }` | `gameStore.setFlag(name, value)` for every entry |
| `clearFlag` | `'name'` | `gameStore.clearFlag(name)`; the flag is unset, so `getFlag` returns `undefined` and `notFlag` passes |
| `addStatusEffect` | `{ id, entity? }` | Adds the status to `entity`: `'player'` (default, the leader) or `'speaker'` (the entity passed to `open`) |
| `removeStatusEffect` | `{ id, entity? }` | Same targeting as `addStatusEffect` |
| `learnAbility` | `'abilityId'` | `gameStore.learnAbility(leaderId, id)` |
| `giveItem` | `{ id, qty? }` | Spawns a **real item entity** from template `id` into the leader's container: `spawnItemEntity(id, { containerId: leaderId, quantity: qty })`. It shows up in the inventory like any looted item |
| `takeItem` | `{ id, qty? }` | Walks the leader's items (equipped included) with that `templateId`, removes whole stacks or decrements the last one until `qty` is consumed. Never fails: if the player has less, it takes what exists |
| `endDialog` | any | Sets the return flag; the store closes the dialog right after this effect batch |

`qty` defaults to `1` for `giveItem` and `takeItem`. An unknown effect key logs `[dialog] unknown effect key` and is skipped; the other effects in the batch still run (unlike conditions, a typo does not abort).

`addStatusEffect` with `entity: 'speaker'` does nothing when `open` was called with `speakerId = null` (narrator-only dialog), because there is no speaker entity in the context.

## Authoring example

Trimmed from `apps/playground/content/dialogs/guard-captain.yaml`:

```yaml
dialogId: guard_captain_gate
startNode: greeting
nodes:
  greeting:
    speaker: guard_captain
    text: Halt. State your business, traveler.
    textVariants:
      - if: { flag: met_guard_captain }
        text: Back again, are you? Keep moving.
    cameraShot: three-quarter
    choices:
      - text: I'm here looking for work.
        tagPrefix: FIGHTER
        conditions:
          - class: fighter
        next: fighter_offer
      - text: Step aside. You don't want trouble.
        tagPrefix: INTIMIDATION
        check: { skill: intimidation, dc: 14 }
        onSuccess: { next: intimidated }
        onFailure:
          next: intimidation_failed
          effects:
            - setFlag: { guard_hostile: true }
      - text: Never mind. Goodbye.
        next: __end
        effects:
          - setFlag: { met_guard_captain: true }
```
